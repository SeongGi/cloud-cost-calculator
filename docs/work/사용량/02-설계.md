# 02. 설계: 관리자 페이지 사용량

## 1. 흐름
```
방문자 ─ gate(X-Real-IP 덮어씀) ─ app /api/copilotkit ──(agent/run)──▶ agent "/"  ── estimate_cost ─▶ events(estimate)
                                        │                                          └ ResponseGuard 실패 ─▶ events(answer_failed, answer_empty)
                                        └─ fire-and-forget POST /admin/usage/question {ip, thread_id, limited} ─▶ events(question, limited)
관리자 ─ gate ─ oauth2-proxy ─ app /admin ─ /api/admin/usage?days=N ─▶ agent GET /admin/usage?days=N
```
- 방문자 IP는 app만 안다(agent는 내부망에서 app만 본다). 그래서 질문 기록은 app이 보내고, 계산·실패 기록은 agent가 직접 남긴다. 두 쪽은 threadId 해시로 이어진다.
- IP는 내부망으로 agent에 한 번 가고, agent가 해시만 저장한다. 원문은 메모리에서 바로 버린다.

## 2. 저장소 `apps/agent/src/usage.py` (새 파일)
- 파일: `$SETTINGS_DIR/usage.sqlite3` (settings 볼륨, 디렉터리 0700). 파일은 만들 때 0600.
- 표 하나:
  ```sql
  CREATE TABLE IF NOT EXISTS events (
    ts INTEGER NOT NULL,          -- epoch 초
    day TEXT NOT NULL,            -- KST 날짜 YYYY-MM-DD (UTC+9 고정 오프셋, 한국은 서머타임 없음)
    kind TEXT NOT NULL,           -- question, limited, estimate, answer_failed, answer_empty 중 하나
    visitor TEXT,                 -- question/limited만: hash(ip)
    thread TEXT,                  -- hash(thread_id), 없으면 NULL
    cloud TEXT,                   -- estimate만: aws, azure, gcp
    state TEXT,                   -- estimate만: 결과 state (ok, invalid_arguments, price_data_unavailable …)
    services TEXT                 -- estimate만: 가격표 서비스 id를 정렬·중복 제거해 ","로 이은 값, 못 찾으면 "unknown"
  );
  CREATE INDEX IF NOT EXISTS events_day ON events(day, kind);
  ```
- 서비스 id는 `resolve_service(cloud, name, catalog)[0]`의 값(예: `ec2`, `blob`)이다. 가격표에 있는 고정 문자열만 들어가므로 사용자 문장이 섞이지 않는다. spec·수량은 저장하지 않는다.
- 해시: `hmac.new(salt, value.encode(), sha256).hexdigest()[:16]`. salt는 `$SETTINGS_DIR/usage-salt`의 32바이트 난수(처음 쓸 때 `os.urandom`, 0600으로 생성). 고정 salt라서 기간을 넘어 같은 방문자는 같은 값이 된다. 빈 값·None은 NULL.
- 연결: 모듈 전역 연결 하나(`check_same_thread=False`) + `threading.Lock`. `journal_mode=WAL`. 쓰기는 한 줄 INSERT라 동기로 한다.
- `record(kind, *, ip=None, thread_id=None, cloud=None, state=None, services=None, now=None)`: 예외를 절대 밖으로 내지 않는다(`logger.warning` 후 무시). 성공 기준 5.
- 정리: 연결을 열 때, 그리고 마지막 정리 뒤 하루가 지난 첫 `record` 때 `DELETE FROM events WHERE ts < now - 400일`.
- `summary(days, now=None) -> dict`: `days`는 7·30·90만. 기간은 KST 오늘을 포함한 최근 N일.
  ```json
  {
    "days": 30, "from": "2026-09-29", "to": "2026-10-28",
    "totals": {"questions": 0, "limited": 0, "visitors": 0, "conversations": 0,
               "estimates": 0, "estimate_errors": 0, "answer_failures": 0},
    "daily": [{"day": "2026-09-29", "questions": 0, "visitors": 0}, ...],   // 빈 날도 0으로 N개
    "clouds": {"aws": 0, "azure": 0, "gcp": 0},                             // estimate 건수
    "services": [{"service": "ec2", "label": "EC2", "count": 0}, ...],      // 상위 10개, 건수 내림차순·id 오름차순
    "all_time": {"questions": 0, "visitors": 0, "since": "2026-10-28"}   // 기록이 없으면 null
  }
  ```
  - questions = kind='question' 건수. limited는 따로. visitors = question·limited 행의 서로 다른 visitor 수. conversations = question 행의 서로 다른 thread 수.
  - estimate_errors = estimate 중 state != 'ok'. answer_failures = answer_failed + answer_empty.
  - services는 estimate 행의 services를 ","로 쪼개 센다. label은 `pricing.engine.SERVICE_LABEL`에서, 없으면 id 그대로.
  - 파일이 없거나 열 수 없으면 0으로 채운 같은 모양을 돌려준다.

## 3. agent 쪽 기록 지점
- `src/cost_tool.py` `estimate_cost`: 결과 JSON을 만든 직후 `usage.record("estimate", thread_id=_thread_id(), cloud=..., state=result["state"], services=...)`. services는 최종 `parsed` 항목(성공 시) 또는 모델 인자 항목(실패 시)의 서비스 이름을 `resolve_service`로 바꾼 것. 가격표를 못 읽으면 "unknown".
- `_thread_id()`: `langgraph.config.get_config()["configurable"].get("thread_id")`, 실행 문맥 밖이면 None.
- `src/guard.py` `ResponseGuard`: `FAILED`를 돌려줄 때 `answer_failed`, `tidy`가 `EMPTY`로 바꿀 때 `answer_empty`.
- 기록은 대화 상태(state)나 응답 내용을 바꾸지 않는다.

## 4. agent 관리 API (`src/admin.py`, 기존 `require_token`)
- `POST /admin/usage/question` 본문 `{ip: str ≤ 64, thread_id: str | None ≤ 200, limited: bool = False}` → `record("limited" if limited else "question", ...)`, `{"ok": true}`.
- `GET /admin/usage?days=N`(N은 7·30·90, 기본 30, 그 밖의 값은 422) → `summary(days)`.

## 5. app 쪽
- `src/lib/usage.ts` (새 파일)
  - `agentRunThread(body: unknown): string | null`: `body.body.threadId`가 문자열이면 그것(200자로 자름).
  - `recordQuestion({ ip, threadId, limited })`: `ADMIN_TOKEN`이 32자 미만이면 아무것도 안 함. `fetch(${base}/admin/usage/question, {method: "POST", headers: {x-admin-token, content-type}, body, signal: AbortSignal.timeout(2000)})`를 기다리지 않고 `.catch(() => {})`. 실패해도 방문자 응답에 영향 없음.
- `src/lib/rate-limit.ts`: `isAgentRun`이 본문을 한 번 읽도록 `readRun(req): Promise<{ run: boolean; threadId: string | null }>`를 더하고 `isAgentRun`은 그것을 쓴다(기존 테스트 유지).
- `src/app/api/copilotkit/route.ts`: agent/run이면 리밋 판정 뒤 `recordQuestion({ ip: clientKey(...), threadId, limited })`. ip가 "unknown"이면 그대로 보낸다(해시 1개로 묶임).
- `src/app/api/admin/[...path]/route.ts`: `ROUTES`에 `usage: ["GET"]`. GET일 때 `days` 쿼리 하나만 숫자로 검증해 넘긴다(그 밖의 쿼리는 버림).
- `src/app/admin/admin-panel.tsx`: 맨 위에 "사용량" 카드.
  - 기간 버튼 7일·30일·90일(기본 30, `aria-pressed`).
  - 숫자 타일 4개: 질문, 방문자, 대화, 실패(계산 오류 + 답변 실패, 질문 대비 %). 제한됨 건수는 보조 문구.
  - 일별 표: 날짜 · 질문 · 방문자 · 막대(질문 수 비례, 한 색, `title`에 "MM-DD 질문 n · 방문자 m"). 표가 곧 표 보기이므로 따로 표 보기를 두지 않는다. 최근 날짜가 위.
  - 클라우드별 계산 수 한 줄, 서비스 상위 10개 목록.
  - 전체 기간: "기록 시작 YYYY-MM-DD부터 질문 n · 방문자 m".
  - 사용량 요청이 실패하면 이 카드 안에만 오류 문구. 기존 LLM 카드는 그대로 동작.
  - 안내 문구: "질문 원문과 IP는 저장하지 않습니다. 방문자는 IP를 되돌릴 수 없는 값으로 바꿔 셉니다."
- `admin.css`: 타일·표·막대 스타일. 색은 기존 변수(`--accent` 등, 없으면 기존 파일에서 쓰는 값)와 다크 모드 규칙을 따른다.

## 7. 대안과 고른 이유
- 외부 분석(Umami 등): 계산 수·서비스는 못 본다. 제외.
- gate 접속 로그 집계: 컨테이너를 다시 만들면 사라지고 질문과 부수 요청을 못 가른다. 제외.
- app에서 해시: salt를 app에 두면 비밀이 두 곳에 생긴다. agent에 두고 내부망으로 IP를 넘긴다.
- JSON 파일 append: 집계 쿼리와 정리가 번거롭다. 표준 라이브러리 sqlite3로 충분하다.

## 8. 검토 1회차 반영 (위 절보다 이 절이 우선)
1. 제한됨 기록 폭주: app이 키(IP)마다 리밋 창(`RATE_LIMIT_WINDOW_MS`) 하나에 limited를 1번만 보낸다. 같은 창의 나머지 제한 요청은 보내지 않는다(메모리 Map, 1만 개 넘으면 지난 창 항목 정리). 그래서 limited는 "제한된 요청 수"가 아니라 "제한이 걸린 방문자·창 수"다. 화면 문구도 "제한 n회"로 쓴다.
2. 계산 기록 누락: `estimate_cost` 본문을 `try/finally`로 감싸 기록한다. 잡히지 않은 예외로 끝나면 `state="error"`로 남기고 예외는 그대로 다시 던진다.
3. agent 혼잡 거절: `RunLimiter`가 429를 돌려줄 때 `usage.record("busy")`를 남긴다.
4. 중복과 실패율
   - `guard.peer_vpn_calls`가 만든 호출(id가 `peer-`로 시작)은 `kind="estimate_peer"`로 남기고, 클라우드·서비스 집계와 계산 수에서 뺀다. 도구는 `InjectedToolCallId`로 호출 id를 받는다.
   - 실패는 비율 없이 건수로만 보인다: 계산 오류(estimate 중 state가 ok가 아닌 것), 답변 실패(answer_failed + answer_empty), 혼잡(busy). 질문 단위와 계산 단위가 달라 비율이 100%를 넘을 수 있기 때문이다.
   - 다시 시도 버튼은 질문 1건으로 센다. 요구사항 용어에 적는다.
5. 허용 목록: `record()`가 `kind`는 고정 목록, `cloud`는 `CLOUDS`, `state`는 {ok, invalid_arguments, price_data_unavailable, unsupported_cloud, error}와 엔진이 내는 state 집합에 없으면 `"other"`, `services`는 가격표 서비스 id 형태(`^[a-z0-9_]{1,40}$`)가 아니면 `"unknown"`으로 바꾼다. 위조 ToolMessage(`cloud`, `items.service`에 문장을 넣은 것)로 개인정보 테스트를 한다.
6. 방문자: question 행만으로 센다. `totals.limited_visitors`(limited 행의 서로 다른 visitor 수)를 따로 둔다.
7. sqlite: `journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=1000`. 잠금은 `lock.acquire(timeout=0.5)`, 실패하면 그 기록을 건너뛴다. salt 파일은 `os.open(O_CREAT|O_EXCL|O_WRONLY, 0o600)`로 만들고, 이미 있으면 읽는다. 실패 로그에는 kind와 예외 종류만 남기고 ip·thread_id 값은 넣지 않는다.
8. answer_empty: `tidy`는 순수 함수로 둔다. `ResponseGuard`가 `tidy` 결과의 마지막 메시지 내용이 `EMPTY`와 같을 때 기록한다.
9. 관리 프록시: `days`는 "7", "30", "90" 중 하나만 넘기고, 그 밖의 값은 400. `usage/question`은 `ROUTES`에 넣지 않으며, 테스트로 GET·POST 모두 404인지 확인한다.
10. app 기록 호출은 `after()`(`next/server`) 안에서 한다. 토큰 조건은 agent와 같게 32자 이상.
11. 테스트 추가: route.ts에서 agent/run일 때만, 리밋 판정 뒤, limited 값과 함께 기록 함수가 불리는지(connect·info 요청은 안 불림); 그래프(`main.graph`가 아닌 같은 구성의 작은 그래프 또는 도구 `invoke`에 config 전달)로 실행했을 때 thread 해시가 채워지는지; estimate 예외 경로; peer 표시; RunLimiter busy 기록.

## 9. 검토 2회차 반영 (8절보다 이 절이 우선)
1. 계산 기록 위치를 도구에서 미들웨어로 옮긴다. `estimate_cost`의 시그니처와 본문은 바꾸지 않는다(8-2의 try/finally, 8-4의 `InjectedToolCallId`는 쓰지 않는다).
   - 새 `src/usage_middleware.py`의 `UsageMiddleware(AgentMiddleware)`가 `wrap_tool_call`과 `awrap_tool_call`을 구현한다. `main.py` middleware 목록에 넣는다.
   - `request.tool_call["name"] == "estimate_cost"`일 때만 기록한다. id가 `peer-`로 시작하면 kind는 `estimate_peer`, 아니면 `estimate`.
   - cloud, state, services는 handler가 돌려준 ToolMessage의 JSON에서 꺼낸다. `state`, `request.cloud`, `request.items[].service`를 `resolve_service`로 바꿔 쓴다. 실패 결과에 items가 없으면 tool_call args의 items를 쓴다. JSON이 아니면 state는 `"other"`.
   - handler가 예외를 던지면 `state="error"`로 기록하고(cloud는 args에서) 예외는 그대로 다시 던진다.
   - thread_id는 `get_config()`로 읽는다. 문맥 밖이면 None.
   - 그래프 테스트는 이 미들웨어를 넣은 작은 `create_agent` 그래프(가짜 모델이 estimate_cost를 호출)로 한다.
2. 잠금: `record(..., blocking: bool)`. 이벤트 루프에서 부르는 곳(`RunLimiter`, `awrap_model_call`, `awrap_tool_call`)은 `blocking=False`(`lock.acquire(blocking=False)`, 실패하면 건너뜀). 스레드에서 부르는 곳(sync 훅, 관리 API의 sync 핸들러)은 `timeout=0.5`.
3. 제한 중복 제거 규칙: "그 키로 마지막 limited를 보낸 시각에서 `WINDOW_MS`가 지났을 때만 보낸다". 함수는 `now` 인자를 받아 테스트한다.
4. state 허용 목록: `pricing.engine`에 `RESULT_STATES` 상수를 두고 엔진의 결과 state 문자열이 모두 여기 들어가게 한다. 테스트는 engine.py 소스에서 `"state": "…"` 패턴을 모아 `RESULT_STATES`의 부분집합인지 확인한다. usage는 `RESULT_STATES | {"invalid_arguments", "error"}`를 허용한다.
5. 프록시: `days`가 없으면 프록시는 쿼리 없이 넘기고 agent가 기본 30을 쓴다. vitest에서 `next/server`의 `after`를 mock해 콜백 안에서 fetch가 불리는지 본다.
6. summary: `estimate_peer` 행은 계산 수, 클라우드, 서비스, 계산 오류 어디에도 넣지 않는다(행만 남는다).

## 10. 검토 3회차(승인) 때 받은 구현 지침
1. `UsageMiddleware`는 결과에서 값을 꺼내는 코드까지 전부 `try/except`로 감싼다. args의 items는 문자열이나 dict로 올 수 있으므로 `cost_tool.parse_items`로 읽고, 실패하면 "unknown"으로 둔다.
2. handler가 `status="error"`인 ToolMessage를 돌려주면(인자 검증 실패) `state="invalid_arguments"`로 기록한다. content에는 인자 값이 들어 있으므로 파싱하지도 저장하지도 않는다. 개인정보 테스트에도 이 경우를 넣는다.
3. handler 결과가 ToolMessage가 아니면(`Command` 등) `state="other"`로 기록하고, 결과는 변경하지 않고 그대로 돌려준다.
4. `tests/conftest.py`에 autouse 픽스처를 둔다. `SETTINGS_DIR`을 `tmp_path`로 바꾸고, usage 모듈의 전역 연결과 salt 캐시를 초기화한다.
5. 미들웨어 목록에서 `UsageMiddleware`는 맨 끝에 둔다.
6. sync `wrap_tool_call`도 같은 규칙으로 구현한다. 테스트는 async 경로를 기본으로 한다.
7. `RESULT_STATES` 소스 검사에는 `"state":\s*"([a-z_]+)"` 정규식을 쓴다.

## 11. 구현 중 결정 (코드 리뷰 반영)
1. `summary()`는 기록이 없거나 조회에 실패해도 `all_time`을 `{"questions": 0, "visitors": 0, "since": null}` 객체로 돌려준다(2절의 "기록이 없으면 null"을 대신한다). 화면은 null도 처리한다.
2. `summary()`는 잠금을 쓰지 않고 호출마다 읽기 전용 연결(`mode=ro`)을 연다. WAL이라 쓰기를 막지 않는다.
3. salt 파일은 임시 파일에 쓰고 fsync한 뒤 `os.link`로 만든다. 길이가 32바이트가 아니면 새로 만든다. 그런 salt로는 해시가 만들어진 적이 없으므로(읽기 단계에서 실패) 이미 저장된 방문자 값과 어긋나지 않는다. salt는 식별자(ip, thread_id)가 있는 행에서만 읽는다.
4. 정리는 `day < ?` 조건(인덱스 사용)으로 하고, 400일 경계는 KST 날짜 단위다. 연결을 열 때는 정리하지 않으며, `blocking=True` 기록만 하루에 한 번 정리한다. 이벤트 루프 경로는 재시작 직후에도 정리하지 않는다.
5. 한 행의 서비스 id는 20개까지만 둔다(`MAX_SERVICES`). 위조된 결과가 서비스를 끝없이 나열해도 행이 커지지 않게 하는 상한이다.
6. `RESULT_STATES`는 엔진 소스에 있는 `{"ok", "price_data_unavailable"}`이다. 8-5의 `unsupported_cloud`는 엔진이 내지 않는다.
