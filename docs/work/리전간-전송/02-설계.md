# 02. 설계: 리전 간·인터넷 데이터 전송 비용

3차본(1차 지적 12건은 9절, 2차 지적 3건은 10절에 대응 표).

## 1. 모델링

출발지는 견적의 리전(`estimate(region=...)`)이다. 도착지는 같은 서비스 안의 **사양 대안(family)**으로 둔다.

- 서비스 id: 세 클라우드 모두 `data_transfer`(화면 이름 "데이터 전송", 서비스군 "네트워크").
- 가격표 키(클라우드마다 4개):
  - `data_transfer.internet`: 인터넷으로 나가는 전송, 세 리전 모두 가격 있음.
  - `data_transfer.to_<도착 리전 코드, 하이픈은 밑줄>`: 다른 리전으로 나가는 전송. 도착 리전 자신에는 가격이 없다(예: `to_ap_northeast_1`은 서울과 버지니아에만 가격이 있음).
- 엔진은 이미 `reg in item["prices"]`인 키만 고르므로, 견적 리전이 서울이면 대안은 인터넷·도쿄·버지니아 세 개가 된다.
- 단위: `quantity_unit "gb"`, `per "gb"`, `quantity_scale 1`, `hours 1`. 기존 NAT 처리 데이터 항목과 같다. GCP는 GiBy 단가를 기존 `cloud_nat`처럼 `convert 1`로 GB 단가로 쓴다(기존 관례).
- 한 견적에 인터넷 전송과 도쿄 전송을 함께 넣으면 spec이 다르므로 두 줄이 된다(엔진의 기존 동작).

## 2. 가격표 명세(spec) 변경

### 공통: 항목별 리전 목록
명세 항목에 선택 필드 `"regions": [...]`를 추가한다. 있으면 빌더는 그 리전만 조회하고(나머지 리전은 조회도 경고도 하지 않음), 완전성 검사도 이 목록 기준으로 한다. 없으면 지금처럼 전체 리전이다.
- AWS: `todo`를 만들 때 `region in spec_regions(k)`인 키만 넣고, 마지막 `len(prices[key]) != len(regions)` 검사를 항목별 목록으로 바꾼다.
- Azure: 리전 반복을 항목별 목록으로, 검사도 같게.
- GCP: `for region in cfg["regions"]` 반복과 검사를 항목별 목록으로.
- `test_catalogs_complete`도 명세의 항목별 목록과 비교한다.

### AWS (`service_code "AWSDataTransfer"`)
- 리전 간: `filters {"fromRegionCode": "{region}", "toRegionCode": "<도착>", "transferType": "InterRegion Outbound"}`.
- 인터넷: `filters {"fromRegionCode": "{region}", "toLocation": "External", "transferType": "AWS Outbound"}`. 첫 구간(beginRange 0, 0~10TB)이 단가다.
- `expect {"product_family": "Data Transfer", "aws_unit": "GB"}`.
- `render()`가 `{prefix}`에 더해 `{region}`도 리전 코드로 바꾼다.

### Azure
도착지에 따라 미터가 다르므로, 명세 항목에 선택 필드 `"by_region": {리전: {"filter": ..., "tier_min": ..., "allow_non_primary": ...}}`를 추가한다. 있으면 그 리전은 이 값이 항목의 `filter`·`tier_min`·`allow_non_primary`를 덮어쓴다. 조회 결과(2026-10-25, `productName 'Bandwidth Inter-Region'`):

| 출발 → 도착 | 미터(armRegionName / meterName) | 단가 |
|---|---|---|
| 한국 중부 ↔ 일본 동부 | `Asia` / `Intra Continent Data Transfer Out` | $0.08 |
| 한국 중부·일본 동부 → 미국 동부 | `Intercontinental` / `Inter Continent Data Transfer Out - ASIA To Any`, tier_min 5 | $0.08 |
| 미국 동부 → 한국 중부·일본 동부 | `Intercontinental` / `Inter Continent Data Transfer Out - NAM or EU To Any`, tier_min 5 | $0.05 |

- 인터넷: `serviceName 'Bandwidth'`, `productName 'Rtn Preference: MGN'`, `meterName 'Standard Data Transfer Out'`, `armRegionName '{region}'`, `tier_min 100`, `allow_non_primary true`.
- 구현자는 위 미터의 `isPrimaryMeterRegion` 값을 확인해 `allow_non_primary`를 정한다. `expect.unitOfMeasure "1 GB"`.

### GCP (`catalog_service "Compute Engine"`, `scope "regional"`)
- 리전 간: `match "^Network Inter Region Data Transfer Out from (Seoul|Japan|Americas) to <Seoul|Japan|Americas>$"`. 빌더의 `pick()`이 `region in serviceRegions`로 거르므로 출발 리전마다 정확히 하나가 남는다(조회로 확인함).
- 인터넷: `match "^Network Internet Data Transfer Out from (Seoul|Tokyo|Americas) to South Korea$"`. 한국 사용자 대상 단가로 고정하고, 라벨에 "(한국 사용자 대상)"을 넣는다.
- `expect_unit "GiBy"`, `convert 1`. 첫 유료 구간은 기존 `first_paid_price()`가 고른다.

### 라벨
대안 선택 상자에 도착지가 보이게 쓴다. 예: "도쿄(ap-northeast-1)로 리전 간 전송", "인터넷으로 나가는 전송(첫 10TB 구간)", GCP "인터넷으로 나가는 전송(한국 사용자 대상)".

### 별칭(aliases)
`"data transfer"`, `"데이터 전송"`, `"전송"`, `"리전 간 전송"`, `"inter region"`, `"inter-region data transfer"`, `"egress"`, `"인터넷 전송"`, `"bandwidth"`(Azure)를 `data_transfer`로 해석한다.

## 3. 엔진 (`pricing/engine.py`)

- `FAMILY_PATTERNS` 세 클라우드에 `r"^data_transfer\."` 추가, `GROUPS["네트워크"]`와 `SERVICE_LABEL`에 `data_transfer` 추가.
- `REGION_ALIASES`에 `"일본"`, `"japan"`(도쿄 리전)과 Azure `"virginia"`, `"버지니아"`(eastus)를 추가한다.
- `service_from_spec`은 `data_transfer`를 후보에서 뺀다("internet gateway" + spec "internet"이 데이터 전송으로 바뀌지 않게).

### 도착지 해석: `transfer_destination(cloud, text, reg, catalog) -> (dest, source)`
`dest`는 `"internet"`, 리전 코드, `""`(정하지 못함), `"?"`(범위 밖 도착지를 말함) 가운데 하나다. `source`는 문장이 출발지로 지목한 리전 코드이거나 `""`이다.
1. 리전 언급 찾기: `REGION_ALIASES[cloud]`의 별칭과 가격표 리전 코드. 라틴 문자 별칭은 앞뒤가 라틴 문자가 아닐 때만, 한글 별칭은 바로 뒤에 "어"가 오지 않을 때만 인정한다("한국어", "business" 제외).
2. 출발지: 언급 바로 뒤에 "에서"가 오거나 앞에 "from "이 오면 출발지다. 출발지 언급은 도착지 후보에서 뺀다. 견적 리전과 같은 언급도 도착지 후보에서 뺀다.
3. 인터넷: `인터넷`, `internet`이 있으면 인터넷이다. 다른 단어(egress, outbound, 아웃바운드, 외부)는 방향 표현일 뿐이므로 인터넷으로 보지 않는다.
4. 판정: 인터넷이면 `"internet"`이 이긴다("한국 사용자에게 인터넷으로"처럼 리전 이름이 사용자 위치일 수 있음). 아니면 도착지 후보가 정확히 하나일 때 그 리전 코드다. 후보가 둘 이상이면 `""`이다.
5. 범위 밖: 1~4보다 먼저 본다. 모델이 넣은 spec이 가격표 밖 리전 코드 모양(`[a-z]{2,}-[a-z]+-?\d`)이거나 범위 밖 지명 목록(싱가포르, 유럽, 오사카, 프랑크푸르트, 런던, 시드니, 홍콩, 뭄바이, 서부, singapore, europe, osaka, frankfurt, london, sydney, hong kong, mumbai, west 등)에 맞을 때만 `"?"`이다. "다른 리전", "DR 리전", "CDN" 같은 그 밖의 표현은 `""`이다. 사용자 문장에는 이 판정을 쓰지 않는다.
6. 출발지 표현은 `별칭\s*(리전|region)?\s*에서`와 `from\s+별칭`으로 찾는다("도쿄 리전에서").

### `estimate()` 처리
- 서비스가 `data_transfer`이면 spec으로 먼저 해석하고, `""`이면 사용자 문장(`user_text`)으로 한 번 더 해석한다. `spec_from_text`는 이 서비스에서 건너뛴다.
- `dest`가 인터넷이나 리전 코드면 spec을 그 값으로 바꾼다. 리전 코드 `ap-northeast-1`의 토큰 {ap, northeast, 1}은 키 `data_transfer.to_ap_northeast_1`의 토큰에 포함되므로 기존 매칭이 그대로 동작한다.
- `dest == "?"`: 줄은 만들되 `_mark_missing(line, 원래 spec, has_alternatives=True)`로 합계에서 뺀다("싱가포르", "europe").
- `dest == ""`: 프로젝트의 고정 규칙(가장 싼 대안이 기본값)을 따른다. 다만 spec이나 문장에 인터넷 단서(egress, outbound, 아웃바운드, 외부, 다운로드, 사용자, 고객, 트래픽)만 있으면 인터넷을, 복제 단서(리전, region, 복제, replication, 백업, DR)만 있으면 가장 싼 리전 간 대안을 spec 단서로 쓴다. 둘 다 있거나 둘 다 없으면 가장 싼 대안이다. 어느 경우든 줄 note는 "도착지를 알 수 없어 <라벨>로 계산했습니다(선택 상자로 변경)"이다.
- `source`가 있고 견적 리전과 다르면 note: "말씀하신 출발지(<라벨>)가 아니라 견적 리전 <라벨> 기준으로 계산했습니다. 출발 리전을 바꾸려면 리전을 지정해 주세요."
- 포함된 데이터 전송 줄이 있으면 notes에 한 문장을 더한다: "데이터 전송은 첫 유료 구간 단가를 전체 수량에 곱했습니다. 무료 구간과 대량 할인 구간은 반영하지 않으므로 실제 청구액보다 많게 잡힐 수 있습니다. 들어오는 전송과 같은 리전 안 전송은 계산하지 않습니다." GCP 인터넷 줄이 있으면 "Google Cloud 인터넷 전송은 한국 사용자 대상 단가입니다."를 더한다.

### 공개 함수 `normalize_transfer_items(cloud, items, region, user_text) -> list[dict]`
`data_transfer` 항목의 spec을 해석 결과(인터넷이나 리전 코드)로 바꾼 사본을 돌려준다. 도착지를 정하지 못해 기본값을 고른 경우에도 그 기본값을 spec에 넣고 `"transfer_default": true`를 표시한다. `"?"`이면 원래 spec을 둔다. 다른 항목은 그대로다. region은 `resolve_region`으로 풀어 `estimate`와 같은 출발지를 쓴다. 같은 입력에 두 번 적용해도 결과가 같다. `estimate`는 `transfer_default`가 있는 항목에 "도착지를 알 수 없어" 안내를 붙인다.

## 4. 이어지는 질문 (`src/cost_tool.py`)

- 병합 여부와 상관없이, 이번 요청의 항목에 `normalize_transfer_items(cloud, parsed, region or prev_region, text)`를 먼저 적용한다. 그래서 저장되는 `request.items`에 도착지(기본값 포함)가 남고, 다음 차례의 문장이 바뀌어도 도착지와 금액이 유지된다.
- `merge_items`는 정규화된 spec끼리 비교하므로 "도쿄"와 "tokyo"가 같은 줄이 된다. 앞 줄이 리전 코드이고 이번이 "internet"이면 서로 다른 줄로 더해진다.
- 앞 줄이 `transfer_default`이면 spec이 빈 줄과 같게 보고 이번 항목으로 교체한다(사용자가 도착지를 밝힌 것). 교체할 때 `transfer_default`는 이번 항목의 값으로 바꾼다.

## 5. 프롬프트 (`src/prompt.py`)

- 7행을 바꾼다: NAT·방화벽이 처리하는 데이터는 그 서비스의 gb로 두고, 다른 리전이나 인터넷으로 나가는 전송량은 `service "data transfer"`, spec에 도착지(예: 도쿄, 미국, 인터넷)를 넣는다. region에는 출발 리전을 넣는다.
- 예시: "AWS 서울에서 도쿄로 매달 1TB 복제" → `cloud=aws, region="ap-northeast-2", items=[{service:"data transfer",spec:"도쿄",gb:1000}]`.

## 6. 가격표 생성과 갱신

- 기존 항목은 다시 빌드하지 않는다. 새 키만 담은 임시 명세로 세 빌더를 돌리고, 결과 항목만 번들 가격표의 `items`에 더한다. `as_of`는 그대로 둔다. 각 단가에 API 게시일(AWS `published`, Azure `effective_start`, GCP `effective_time`)이 남는다.
- `paths.readable_catalog_path`: 갱신본이 번들 가격표의 키 일부를 갖고 있지 않으면 번들을 쓴다(코드가 새 항목을 더한 직후의 갱신본은 낡은 것으로 본다).
- `refresh.refresh_one`: 이월 대상 키를 "이전 가격표 ∪ 번들 가격표"의 키로 넓힌다. 새 빌드에서 빠진 키는 이전 가격표에 있으면 그 값을, 없으면 번들 값을 이어 쓴다.
- AWS 번들의 `source` 표기(Query API)와 새 항목의 실제 출처(bulk)가 다르다. 두 경로 모두 같은 AWS Price List 데이터이므로 표기는 바꾸지 않고 04-검증.md에 기록한다.

## 10. 2차 검토 대응

| 지적 | 대응 |
|---|---|
| 1 기본값 도착지 미저장 | 3절 공개 함수: 기본값도 spec에 저장하고 `transfer_default` 표시, 4절 교체 규칙 |
| 2 인터넷 기본값과 고정 규칙 | 고정 규칙 유지. 인터넷은 문장 단서가 있을 때 spec 단서로만 고름 |
| 3 범위 밖 판정 | 3절 5: 리전 코드 모양과 지명 목록에 맞을 때만 `"?"` |
| 구현 시 확인 | "리전에서" 출발지(3절 6), "미국 서부"는 지명 목록의 "서부/west"로 `"?"`, 새 견적에도 정규화(4절), Azure tier_min 5, paths는 mtime 캐시 |

## 11. 3차 검토 대응 (설계 루프 3회 종료)

3차 검토도 "수정 필요"였다. 남은 지적은 1건이며, 검토자가 제안한 해법을 그대로 적용했다.

| 지적 | 대응 |
|---|---|
| 병합 전 기본값 채우기가 "수량만 바꿈" 신호를 지움 | 병합 전에는 사용자가 밝힌 도착지만 정규화한다. 기본값 채우기와 `transfer_default` 표시는 병합 뒤 항목에 적용한다. 테스트: "인터넷 500GB" → "전송량 2TB로 늘려"는 한 줄 2000GB |
| 구현 시 확인 | 교체 시 `transfer_default` 명시 덮어쓰기, `parse_items` 뒤 정규화, 가격표 안 리전 코드는 `"?"` 아님, "westus2"는 `""`, 두 단서 동시 → 가장 싼 대안, 갱신본 선택과 번들 이월 통합 테스트 |

설계 루프는 3회 안에 공식 승인을 받지 못했다. 사용자에게 이 사실과 마지막 쟁점의 처리 방식을 보고한다.

## 12. 코드 리뷰 반영 후 확정된 차이 (구현이 정본)

- 범위 밖(`"?"`) 판정은 리전 코드 모양과 범위 밖 지명 목록 방식이다(코드 리뷰 3회차에서 잔여 글자 방식을 되돌림). 목록은 `engine.py`에 있다.
- 인터넷 단서: egress, outbound, 아웃바운드, 외부, 다운로드, 사용자, 고객, 트래픽, 온프레미스, on-prem, IDC, 사무실, users, public, 해외, CloudFront.
- 리전 언급 바로 뒤에 사용자·고객·유저·접속(users, customers, clients)이 오면 사용자 위치로 보고 도착지 후보에서 뺀다. 한글 별칭 뒤에 식·인·어가 오거나 "us" 뒤에 달러가 오면 리전이 아니다. 출발지 표현은 "에서", "로부터", "from X", "X to"이다.
- 별칭 추가: "한국 중부"처럼 방위가 붙은 두 단어 별칭, 버지니아의 "us-east"와 "n. virginia".
- `normalize_transfer_items(..., read_text, fill_default)`: 병합 전에는 모델이 준 spec만 정규화하고, 사용자 문장은 추가 의도(추가, 더하, 더 넣, 으로도, 로도, 도 추가)가 있을 때만 읽는다. 기본값 채우기는 병합 뒤에 한다.
- `transfer_default` 줄은 추가 의도가 없을 때만 교체한다. 저장된 도착지가 새 견적 리전과 같아지면 `transfer_dropped`를 남기고 안내한다.
- `paths.py` 캐시 키는 `(st_mtime_ns, st_size, st_ino)`이고, `refresh.py` 이월은 갱신 파일을 우선하며 없을 때 번들 값을 쓴다.
